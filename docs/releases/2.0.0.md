# Core 2.0.0

Release notes for the coordinated five-package `@yuva/*` version 2.0.0.
The authenticated `core-v2.0.0` tag and its seven release assets identify the
published source and bytes; a local candidate alone is not publication evidence.

## Breaking compatibility requirements

- Node.js 24.x is required (`>=24 <25`). Node 22 is no longer supported by the
  current source or this bundle. Previously published 1.x archives remain
  immutable with their original engine metadata and compatibility records.
- `@yuva/auth-core` now declares `@clerk/backend: ^3.16.3` as an optional peer.
  Clerk consumers must declare the SDK directly in their application and update
  their lockfile. Package-root imports and custom request authentication can run
  without Clerk installed. Selecting Clerk credential verification without the
  SDK fails closed with 503; it does not create anonymous access.
- Production users of the core claim-token helpers must configure
  `CLAIM_TOKEN_SECRET` or `UNSUBSCRIBE_SECRET`. The development-only fallback is
  rejected in production. This does not rotate secrets or rewrite existing data.

## Runtime changes

`createRequireAuth` and `createOptionalAuth` accept trusted request-level
`verifyRequest` and explicit `findUser` ports. Clerk remains the default when
those ports are omitted. Custom identity verification requires a valid local
profile, preserves provider/tenant context for the mapper, clears stale request
identity fields, and distinguishes invalid credentials from infrastructure
failures. Existing Clerk token-level injection, reason classification and
signature-only JWKS fallback remain available. Downstream route errors are no
longer reclassified as authentication failures.

The OpenAI transport resolves its endpoint before normalization: an explicit
nonblank `baseUrl`, then nonblank `OPENAI_BASE_URL`, then the official
`https://api.openai.com/v1` default. Gateway-bound products should continue to
require and verify an explicit route. This default change must not be mistaken
for a credential or endpoint migration.

The billing-core, context-engine and admin-core runtime source is unchanged
from core-v1.5.0. The five components share version 2.0.0 to describe one tested
compatibility set. Existing free and paid ledger APIs, numeric execution budgets,
and the explicit provider-default output-token policy remain available.

## Application code and release metadata

The repository also contains application-owned chat persistence/recovery,
versioned product input, provider binding, and a self-hosted authentication
adapter. These files are not part of the five core tarballs and are not copied
into existing applications by a core upgrade. Adopting them requires a separate
product review. The self-hosted adapter requires its own schema/configuration,
same-origin cookie and mail setup, and an explicit existing-account migration
design. It does not provide automatic Clerk account migration.

New bundles record build intent separately from publication, and may include
the source commit and digest of the product-owned starter usage adapter.
Upgrade plans report differences without overwriting application code. A
consumer without that fixed starter path is not required to create one.

## Upgrade and verification

Use a newly published immutable 2.0.0 bundle; never replace 1.5.0 assets. Verify
the authenticated tag/source, manifest digest, archive hashes, exact application
dependency pins and lockfile. Installing packages does not run SQL. The bundle
lists starter migrations 1–7 for starter-schema consumers; this list is not an
instruction to apply starter migrations to a product-owned schema.

Required evidence includes actual installed public-package imports, Clerk and
custom-auth contracts with and without the optional SDK, route selection with
intercepted provider transport, unchanged output policies and Credit accounting,
release integrity/provenance checks, and the applicable isolated PostgreSQL
acceptance. Record the final source SHA and results before publication. No live
provider call, production migration, account setup or deployment is implied.
