# Core 1.3.0

Coordinated minor release of all five public `@yuva/*` packages. The additive
interfaces and compatibility fixes from PRs #37, #38 and #39 are included. The
authenticated release manifest records the exact merged main source SHA,
package hashes and tested SDK versions; existing releases remain immutable.

## Changes

- `assembleConversationContext` preserves all supplied chart/context units and
  conversation messages without application budget or priority pruning. Token
  counts are diagnostic; the provider owns its actual context-window limit.
- `loadConversationMessages` reads every oldest-first page from one
  product-authorized conversation. Storage failures propagate instead of
  returning truncated history; repeated or empty continuation cursors fail.
- `reserveFeatureCredits` accepts optional server-owned
  `allowedGrantSourceTypes`. It locks eligible active grants and checks their
  balance before creating a request or reactivating a released attempt, including
  before `resetResult`. Insufficient eligible grants return
  `eligible_grant_sources` without a new reservation or result reset. Active and
  settled requests still replay; omitting the filter retains unrestricted use.
- Responses reasoning configuration accepts `max` and `xhigh` and preserves them
  in SDK request bodies. Streaming, `store: false`, explicit output limits and
  disabled hidden retries remain unchanged. Offline wire tests cover
  `gpt-6-luna` and `gpt-6.1-sol`; provider/model availability remains a product
  configuration responsibility.
- Administrative negative Credit deltas are explicitly PostgreSQL `integer`,
  preventing SQLSTATE `42725` during expiration, deduction and reversal. The
  account lock, balance guard, atomic ledger and rollback behavior are preserved.
- Signup grants retain posted-ledger confirmation, transaction ID/amount,
  idempotent replay and fail-closed 503 behavior for missing confirmation. Auth
  source and product prices are unchanged.

## Compatibility and migration

Node 22/24, PostgreSQL 16. No new migrations or automatic SQL execution are
introduced in 1.3.0. Existing legacy ledger/runtime consumers can receive these
fixes without adopting starter OperationStore tables or changing product prices.

The schema qualification documented in [Core 1.2.0](1.2.0.md) still applies to
OperationStore consumers upgrading from 1.1.0: they must adopt and test starter
migrations 003–006 in their own migration sequence. The complete starter schema
remains migrations 001–006. Never apply those starter migrations to Ziwei merely
because the package version changes. Copied setup scripts and product composition
remain consumer-owned.

SDK dependency ranges are unchanged; the owner lock retains OpenAI 4.0.44,
ai 7.0.70, Anthropic 4.0.40 and Clerk 3.16.9. Independent compatibility checks also
passed with the current Ziwei SDK lock at 4.0.36 / 7.0.56 / 4.0.34 / 3.16.3,
including native ESM imports and actual SDK max/xhigh serialization using an
offline fetch. Each consumer must verify its final SDK resolution and package
integrity in its upgrade PR. Historical 1.2.2 archives are not relabeled as this
release's source or publication evidence.

## Validation and distribution

The release-preparation gate requires Node 22/24 CI with real isolated PostgreSQL
schemas, 266 tests with zero skips across all 13 required acceptance suites,
package boundaries, the Web build, operations verification and an independent
Customer Support consumer. Node 24 CI also builds portable API and Web containers.
Regressions cover complete history and paging failures, source-restricted fresh
and released retries, mixed paid/free grants, concurrency, rollback, Signup
confirmation and negative-delta balances. Provider fixtures are deterministic;
no paid Provider invocation is required by this gate.

Publication uses the private GitHub Release `core-v1.3.0` with `manifest.json`,
`manifest.sha256` and the five coordinated npm tarballs. The manifest must have
`development=false` and identify the exact verified merged main SHA. Download
authenticated assets, verify the source/tag and manifest/archive hashes, then
vendor them and update the consumer lock/pin through a separate upgrade PR.
No production deployment, production migration or credential change is included.
