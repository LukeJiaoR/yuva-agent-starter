# Core 1.2.0

Coordinated release of all five public `@yuva/*` packages. Epic #1 is
complete. The existing ledger/runtime ports remain supported; core-v1.1.0 stays
available and is never overwritten. Source SHA and exact dependency versions are
recorded in the attached manifest.

## Changes

- Operation identity, account-scoped idempotency and immutable quotes separate
  provider usage, product pricing, fulfillment and financial state.
- Durable per-call usage retains missing versus zero, estimates, synthetic and
  provider observations, partial failures, request/model provenance and exact
  currency amounts. Hidden SDK retries remain disabled.
- Fixed-operation and token policies share one billing adapter. Rates, limits,
  policy/delivery versions and authorization are frozen; token aggregation rounds
  once. Missing usage defers settlement unless an explicit estimate was accepted.
- Execution budgets persist call/retry/output limits, provider/model paths and
  deadlines. Unknown external execution is preserved after local interruption.
- Settlement persists the result and ledger atomically, supports no-charge
  success and terminal replay, and reconciles uncertain COMMIT acknowledgments.
- Recovery uses durable leases, fencing epochs, original quotes, existing external
  jobs, bounded deadlines and audited manual handling. Late usage cannot rewrite
  a terminal user bill. The CLI defaults to dry-run.
- The optional starter application includes fixed 2-credit and token-priced
  runnable examples, public quote/actual fields and result replay after disconnect.
  Core packages do not require starter-web.

## Compatibility and migrations

Node 22/24, PostgreSQL 16. Package installation never executes SQL. Existing
consumers can upgrade the existing public ports without adopting
starter tables or changing product prices. New operation/usage/settlement/recovery
APIs require the corresponding product-owned persistence implementation.

**Upgrade qualification discovered in the independent consumer regression:**
`createOperationStore` was already exported in 1.1.0. Its 1.2.0 implementation
requires the newer starter schema (including `financial_status`), so an existing
OperationStore consumer cannot perform a package-only upgrade on migrations
001–002. Adopt and test migrations 003–006 in that consumer's own upgrade PR.
This requirement does not apply to consumers using only legacy ledger/runtime
ports. Treat this as an explicit schema compatibility limitation
of 1.2.0, not a blanket additive compatibility promise.

The complete starter application uses migrations 001–006: baseline, operations,
provider usage, execution budgets, settlement and recovery leases. Apply these
only through the starter migration runner for a starter-schema consumer. Never
copy that migration numbering into an unrelated product schema. Copied consumer setup scripts and
product composition are owned by the consumer and are not replaced by a package
upgrade. Adopting the new starter composition is a separate reviewed change.

Back up and validate schema compatibility before migration. Restoring an old
package pin does not undo migrations; the runner rejects an unknown newer schema.
Historical token display values do not imply complete provider usage or cost.

## Validation and scope

The release gate requires Node 22/24 CI with real isolated PostgreSQL schemas,
222 tests with zero skips across 13 required acceptance suites, the Web build and
operations verification. Node 24 CI builds API and Web containers. Tests cover
legacy/new schema equivalence and preserved financial history, process crashes,
COMMIT ambiguity, concurrent recovery, frozen prices and deterministic provider
fixtures. The release-preparation PR must pass this gate before publication.

Media coverage is contract/fixture validation only. No working image/video
adapter, paid provider request, production migration or production deployment is
included. Future image integration remains OpenAI-compatible only (Epic #14).

Download the release from this repository, verify manifest and archive hashes, vendor the
same artifacts in each consumer, update its lockfile, and validate through a
separate upgrade PR before its normal deployment process.
